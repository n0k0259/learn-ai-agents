## From demo to product

You now know how an agent works at its core: an LLM runs the ReAct loop, guided by context, and uses tools to complete the task. The experiments in the earlier lessons show that this mechanism works. They also show how fragile it is:

- the model may hallucinate, inventing tools or parameters that don't exist;
- it may pick the wrong tool;
- it may fail to recover from an error.

A large gap separates a working demo from a reliable product, and those fragilities are exactly what Harness Engineering exists to fix. The first half of the chapter asked what an agent is. This half asks how an agent runs reliably in production.

## Agent = Model + Harness

The formula so far, **Agent = LLM + Context + Tools**, describes the agent's internal composition: a reasoning engine, a working context, and action interfaces. Harness Engineering adds a second, implementation-level view of the same system. The LLM becomes one core component, the Model, and all the supporting code built around it is the Harness.

The two views don't compete; they describe one system at different levels of abstraction. The book switches to the broader word "Model" because harness principles apply to any model that can reason and call tools, not to one particular kind. The Harness keeps the original "Context + Tools" at its core and adds three layers of safeguards:

- **Constrain:** what the agent may and may not do;
- **Verify:** whether it did the thing correctly;
- **Correct:** how to recover when it didn't.

Written out, the production-grade composition is:

> **Agent = Model + Harness**
>
> **Harness = Context management + Tool interfaces + Constraints + Verification + Correction**
>
> **Agent ↔ Environment**

A minimal demo needs only a Model and a Harness that can construct context and expose tools. A production system adds constraints, verification, and correction within that same boundary. Take a refund agent:

- its policy goes into the context;
- permission and amount rules constrain its calls;
- the result is verified against database state;
- after a timeout, it retries or falls back.

Harness engineering studies exactly this runtime and governance code, which sits outside the Model but inside the agent boundary.

More precisely, the Harness is not "everything outside the model". It mediates the interaction between the Model and the Environment, but it does not include the Environment. Tool definitions, call adapters, sandbox permissions, and reset mechanisms belong to the Harness. Files and processes that change inside the sandbox, external databases, web pages, users, and the physical world belong to the Environment. Where each piece is deployed doesn't move this conceptual boundary.

Context management and tool interfaces form the core of the Harness, and three kinds of engineering safeguard are built around them:

| Component | Responsibility and design principle | Practical examples | See chapters |
|---|---|---|---|
| **Context management** | Supplies relevant information. **Information sufficiency:** give the agent enough information to make an informed decision at each step. | System prompts, knowledge bases, agent status bars, Sidecar bypass queries | Chapters 2 & 3 |
| **Tool interfaces** | Defines how the model can act. **Clear interfaces:** use intuitive tool names, provide parameter examples, and explain each tool's limits. | MCP tools, code interpreter, search tools | Chapter 4 |
| **Constraints** | Defines what the agent is allowed to do. **Fail-safe defaults:** keep capabilities disabled until explicitly enabled, as with mobile app permissions. | Claude Code requires user authorization before tool execution by default. | Chapter 4 |
| **Verification** | Checks whether tool execution produced the correct result. **Input isolation:** base security checks on structured data, such as fields returned by tools, rather than on model-generated text that an attacker could influence through prompt injection. | Linting, type checks, validation of tool results | Chapters 5 & 6 |
| **Correction** | Recovers from errors or rolls back failed operations. Attempt recovery before presenting a failure to the user: for example, retry a failed tool call instead of showing an incomplete result. | Automatic retries, resuming generation, escalation to a human after repeated failures (a circuit breaker) | Chapters 2 & 5 |

## The control loop

The book's pseudocode for the basic model control loop places each harness responsibility in the loop:

```python title="control_loop (book pseudocode)"
observation = Environment.observe()
trajectory = [observation]
while true:
	actions = Model(Harness.build_context(trajectory))
	if len(actions) == 0:
		break
	allowed_actions = Harness.constrain(actions)
	observation = Environment.apply(allowed_actions)
	if not Harness.verify(Environment):
		observation = Harness.correct(Environment)
	trajectory.append(allowed_actions, observation)
```

The skeleton deliberately leaves out implementation details. The book gives the complete API message loop in Chapter 2, tools in Chapter 4, and automatic verification in Chapter 5.

Here is the refund agent's action step written against that skeleton. The `harness` and `env` objects are placeholders:

```python title="refund_agent_step.py (illustrative)"
def apply_refunds(actions, env, harness):
    allowed = [a for a in actions if harness.constrain(a)]   # permission + amount rules from policy
    for action in allowed:
        result = env.apply(action)                            # call the refund API
        if not harness.verify(action, env):                   # read back database state, not model text
            result = harness.correct(action, env)             # retry, fall back after timeout, or escalate
        yield action, result
```

:::note[Engineer's note]
Notice what `verify` reads: the database, not the model's reply. If the check parsed the model's "refund issued" message instead, a prompt injection could pass it. Reading structured state from the environment is the input-isolation principle from the table, applied.
:::

## Where production harness code goes

Context and Tools let the agent complete tasks: it understands the task and acts on it. Constrain, Verify, and Correct make sure it does so reliably and safely. They aren't separate from Context and Tools; they are the engineering that keeps those two working in production. As agent products mature, the emphasis between the two groups shifts.

Early agent frameworks focused on Context and Tools: give the model tools and context, and let it complete tasks. Production-grade systems have moved their center of gravity to Constrain, Verify, and Correct. They make sure tool calls are safe, context is managed, and errors can be corrected.

Claude Code illustrates the shift. The vast majority of its Harness code does Constrain, Verify, and Correct, not Context and Tools. The tools themselves (file read/write, command execution, search) are only a small part; the safeguards around them are the true core. They include:

- **Process state management:** tracks which step the agent is executing.
- **Multi-layer context compression:** automatically prunes information when there is too much.
- **Permission classification:** controls which operations need user confirmation.
- **Circuit breaker:** stops retrying after repeated errors, so one failing operation doesn't cascade through the whole system.
- **Error recovery mechanisms:** catch exceptions, roll back to the last stable state, retry, or hand off to a human.

**The industry is shifting from task completion to reliable task completion, making Harness Engineering the core competitive advantage of agent systems.**

## Prompt → context → harness → loop → graph

AI application engineering has moved through a clear sequence of paradigms, each widening the one before.

<Figure caption="Five nested engineering paradigms. Each layer widens the scope of the one inside it.">
<EngineeringParadigms />
</Figure>

- **Prompt Engineering** was the first wave. It improved output quality by refining the natural-language instructions given to the model.
- **Context Engineering** was the second. Optimizing the prompt alone wasn't enough: everything the model can see (system instructions, tool definitions, conversation history, external knowledge) has to be managed systematically.
- **Harness Engineering** was the third. It widens the question from "what information does the model receive" to "what kind of system does the model run in", taking in all the infrastructure outside the model: constraint mechanisms, verification methods, feedback loops, and error recovery.
- **Loop Engineering** came next. It widens the view from a single run to sustained autonomous operation across runs: who discovers the next piece of work, when to verify, and when the task counts as truly done. The book develops this in Chapter 10, alongside multi-agent collaboration systems.
- **Graph Engineering** is the name the industry began using in July 2026 for a higher-level orchestration view. Agent loops, deterministic programs, and human approvals are organized into an explicit execution graph. Nodes provide capabilities, edges define routing and dependencies, and structured state travels along the edges and is persisted at key boundaries.

Josh C. Simmons used the name explicitly in his July 4, 2026 article "We Are Entering the Graph Engineering Phase", summarizing it as nodes, typed edges, and checkpointed state. On July 18, Peter Steinberger asked whether the discussion had shifted from loops to graphs, which helped the name spread. The practices predate the label: the official documentation for LangGraph, Microsoft Agent Framework, and Google ADK describes them as graph orchestration or graph-based workflows.

The five stages don't replace each other; they nest. Prompt Engineering is a subset of Context Engineering, which is a subset of Harness Engineering, which is a subset of Loop Engineering. Loop Engineering is in turn a subset of Graph Engineering, since a single agent loop forms one node in the execution graph. Each layer widens the engineer's scope of concern and influence.

**As models converge in capability and stop being the decisive differentiator, competitive advantage shifts to the engineering outside the model.**

Recent practice supports this. Terminal Bench 2.0 is a benchmark that evaluates an agent's ability to complete complex tasks in a terminal environment. LangChain's coding agent improved on it from 52.8% to 66.5%, jumping from outside the top 30 to the top 5 on the leaderboard. The model didn't change; the Harness did. The agent was made to check its own execution results, detect when it was stuck in a repetitive loop, and refine its reasoning strategy.

## Three principles

Based on Anthropic's experience, successful agent systems follow three core principles.

**Keep it simple.** Start with the simplest solution and add complexity only when it is truly needed. Direct API calls beat complex frameworks, and clear code beats clever abstraction. Every extra layer of abstraction is a new blind spot when you debug.

**Keep it transparent.** Show the agent's planning steps, execution logs, and decision trajectory clearly. This is more than a debugging convenience; it is a precondition for user trust. An error inside a black box is hard to locate or fix from outside.

**Design a well-structured tool interface (ACI, Agent-Computer Interface).** An ACI is designed from the agent's perspective, so the agent finds it easy to understand and use. Traditional APIs are designed from the programmer's perspective. Tool names and parameters should be intuitive, and wherever misuse is likely, the design should make the mistake impossible from the start.

A SIM card's notched corner lets it slide into the tray in only one orientation, and a microwave refuses to heat while its door is open. Manufacturing calls this **poka-yoke**, or **mistake-proofing**: designing products and processes to prevent mistakes or make them immediately apparent. It is used in the Toyota Production System.

A poorly designed tool can make even the strongest model fail repeatedly. The interface is the only channel between model and tool, so a vague interface gets amplified into systemic error.

The next three topics are freestanding but important parts of harness engineering: model selection, orchestration patterns, and guardrails and safety. None of them is one of the five Harness elements proper, but all of them are unavoidable in practice. Model selection follows here; orchestration is covered in [lesson 1.7 (Orchestration: Workflow vs. Autonomous)](/learn-ai-agents/chapter-1/07-orchestration-patterns/), and guardrails and safety in [lesson 1.8 (Guardrails, Safety & the Big Picture)](/learn-ai-agents/chapter-1/08-guardrails-and-big-picture/).

## Choosing a model

Before orchestration patterns comes a practical question: what kind of model should drive your agent? The model is the foundation of the agent's intelligence, and choosing the right one often matters more than any amount of prompt tuning. Releases move too fast for specific version recommendations to stay useful, so the book gives directions instead:

- **Evaluate on your own tasks, not leaderboards.** The book covers evaluation in Chapter 7.
- **Weigh closed against open models.** Closed models, most commonly from OpenAI (GPT/o series) and Anthropic (Claude series), generally lead in capability but cost more and are constrained by the vendor's API policies. At the time of writing, open models lag closed ones by no more than six months and cost substantially less. They support private deployment and fine-tuning, which suits cost-sensitive scenarios and data compliance requirements, so if your scenario doesn't demand the highest capability, an open model is a pragmatic choice. DeepSeek, Kimi, and GLM are among the stronger Chinese models for agent capabilities; tool-calling ability varies widely, so test it in your specific scenario before committing.
- **Check policy boundaries.** A model may be technically able to perform a task while the product hosting it doesn't let users invoke that ability. Vendors draw different boundaries around cybersecurity, model distillation, model extraction, private data, and high-risk operations, and the same task can produce different outcomes in a chat product, a coding agent, and an API. So don't compare only accuracy, price, and speed: on your real tasks, test whether the model is willing to proceed, whether the interface exposes the capability you need, and whether the service terms permit the intended use. For business-critical tasks, prepare a fallback: human handoff or another compliant model.
- **Use a reasoning model for anything multi-step.** Agents make complex decisions, such as multi-step reasoning and tool selection, and models without reasoning tend to perform poorly on them. The exceptions are few: a single simple step, or Computer Use GUI operations that amount to clicking a fixed position, where a non-reasoning model may suffice. The moment multi-step reasoning or dynamic decision-making enters, a reasoning model is essential.
- **Measure output token speed.** It is easy to overlook. Agents typically run many rounds of inference, and each round must finish before the next starts, so output speed directly sets end-to-end latency: a 20-round task that runs 2 s slower per round waits an extra 40 s.
- **Confirm multimodal support** if your agent needs to understand images, audio, or video. There it is a hard requirement, and models differ widely.

<KeyTakeaways>
- Agent = Model + Harness. Harness = context management + tool interfaces + constraints + verification + correction. The agent interacts with the environment.
- A minimal demo needs only context and tools. A production system adds constrain, verify, and correct inside the same boundary.
- The Harness sits inside the agent and outside the model. It mediates the environment but doesn't include it: sandbox permissions are harness, and the files changing inside the sandbox are environment.
- The design principles: information sufficiency, clear interfaces, fail-safe defaults, input isolation, and recovery before surfacing a failure.
- Most of Claude Code's harness code does constrain, verify, and correct. The industry is moving from task completion to reliable task completion.
- Prompt ⊂ context ⊂ harness ⊂ loop ⊂ graph engineering. LangChain went from 52.8% to 66.5% on Terminal Bench 2.0 by changing only the harness.
- Keep it simple, keep it transparent, and mistake-proof the ACI.
- Choose models on your own tasks, and check tool calling, policy boundaries, reasoning support, output speed, and multimodality.
</KeyTakeaways>
